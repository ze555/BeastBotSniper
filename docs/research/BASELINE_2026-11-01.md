The current `src/lib/exitEvidenceReplay.ts` algorithm was re-executed against the repository's committed trade and candle files using the same causal scan conditions:
- 44/78 trades covered (56.4%).
- 34 discretionary EXIT triggers.
- 17 triggers occurred on trades whose recorded final PnL was positive.
- Hypothetical full-exit trigger sum: -1.23R.
- Recorded PnL on the covered subset: +5.24R.
- Trigger-vs-recorded difference: -4.99R.

This is a diagnostic close-price proxy, not a complete execution replay: the candidate exit does not reproduce original partial TP fills, stop movement, fees, spread, or slippage. It is nevertheless a clear rejection of promoting this exit rule unchanged. Keep it out of the production path until a proper fill-aware replay passes.

## Code integration observations
- `apexPredator.ts` imports `reasoningEngine.ts` and `researchLogger.ts`, but does not import `exitEvidenceEngine.ts` or `directionStateEngine.ts`. Their tests do not prove that either engine governs production decisions.
- `exitEvidenceEngine.ts` declared `maxScore: 9` in its decision interface but returned `maxScore: 8`, despite nine possible score points. This branch corrects the returned ceiling and adds a regression assertion.
- `fetchLiq()` in `apexPredator.ts` returns fixed mock values, not measured liquidation data.
- `fetchOI()` returns an empty array on failure. Downstream logic must preserve an explicit unavailable state rather than interpret missing OI as zero change.

## Next gates before any strategy promotion
1. Run repository unit tests, replay, and build on the isolated branch.
2. Build a fill-aware baseline simulator that handles partial exits, stop updates, fees, slippage, and same-candle stop/target ambiguity conservatively.
3. Reconstruct rejected-signal outcomes only where future candle coverage exists; do not infer outcomes from rejection labels.
4. Evaluate separate strategy candidates (trend continuation, confirmed breakout/retest, liquidity sweep/reclaim, momentum expansion) against the same historical windows.
5. Use chronological train/validation/out-of-sample splits and walk-forward checks. Report trade count, net PnL/R after costs, PF, expectancy, max drawdown, exposure, and missed winners/avoided losers.
6. Promote only candidates that beat the untouched baseline out-of-sample and survive stress tests. No live deployment or main-branch merge without explicit approval.
